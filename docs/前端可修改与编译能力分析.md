# 前端可修改与编译能力分析

检查日期：2026-10-14。依据为当前项目文件、原提供压缩包、静态资源清单及HTTP服务代码；没有运行原厂代码构建或修改页面行为。

## 结论

抓取的原平台可以做局部修改，但当前不能作为完整Vue源码工程重新编译。现有文件主要是浏览器运行的编译产物和HTTP响应记录。新增治理工作台有完整HTML/CSS/JavaScript文件，可直接修改；它目前不需要打包编译。

缺失的是原工程源码及构建环境，而不仅是一个build命令。增加打包工具或安装Vue不能把现有编译包自动还原成原工程。

## 现在的页面从哪里来

原页面的服务链路是：

`浏览器请求/home或/dist/js/... → server.mjs按mock/manifest.json查找 → 读取mock/bodies/*.bin → 按HTML/JS/CSS类型返回`

`.bin`只是HTTP响应文件的命名方式，其中可能是文本HTML、JavaScript、CSS，也可能是图片。文件不是Vue组件源码，但文本响应仍可以读取、格式化或修改。

具体示例：

- 首页HTML：`mock/bodies/000000.bin`；`manifest.fallbackDocument`指向该文件。
- 主门户JS：`/dist/js/app.ad46ac39.js`映射到`mock/bodies/000007.bin`。
- 主门户CSS：`/dist/css/app.55f79a10.css`映射到`mock/bodies/000004.bin`。
- 原数据质量应用：`/sjzl/dist/js/app.7e8011d1.js`映射到`mock/bodies/000872.bin`；该JS存在map引用，但map文件缺失。
- 工作台：`server.mjs`直接读取`public/workbench/`中的文件。

因此，只修改`public/index.html`不会改变当前服务实际返回的原首页；当前首页主要由mock中的HTML提供。工作台则可以直接改public/workbench文件。

## 哪些修改可行

| 修改需求 | 原平台编译页面 | 新工作台 |
| --- | --- | --- |
| 改颜色、字体、间距、隐藏元素 | 可修改CSS或注入样式，需要核验其他页面影响 | 直接修改style.css |
| 更换Logo、部分标题和文案 | 可修改对应图片、HTML、配置或编译代码；不能保证所有文案都在同一文件 | 直接修改HTML/JS |
| 增加工作台链接或新按钮 | 可以通过服务端HTML注入或独立脚本实现 | 可直接增加 |
| 改接口地址、菜单数据 | 可修改外部配置、后端返回数据，必要时补丁编译JS | 可直接修改请求和路由逻辑 |
| 改表格列、校验、弹窗逻辑 | 可以分析和修补编译代码，但维护成本高 | 有源码，可正常实现 |
| 新增复杂页面、流程画布 | 不适合在压缩包上持续开发，建议新源码页面承接 | 可以继续开发或迁移到新的源码工程 |
| 重新运行原厂Vue构建 | 当前做不到，源码和构建配置不齐 | 目前直接运行；需要时可建立新的构建工程 |

现有右下角“治理工作台”入口就是server.mjs在原HTML中插入链接，而不是修改原Vue组件重新打包。这证明局部扩展可行，但不代表恢复了原开发工程。

直接改编译JS可能涉及Webpack模块编号、懒加载文件和共享依赖。格式化能提高可读性，不能恢复原Vue文件结构、注释、原始变量名、构建配置或缺失页面。

## source map和另一套静态文件的意义

主平台的部分JS保留sourceMappingURL指向`.map`，但当前文件和压缩包没有这些map。只能判断本地缺失，未检查原站是否仍提供。若以后获取map且包含sourcesContent，可以恢复部分源码；若只有映射和源路径，仍缺原文件。即使恢复部分组件，也需补齐依赖版本、原厂组件和构建配置，不能承诺恢复完整工程。

`public/static/js/app.js`包含开发打包时的模块路径，例如`./src/App.vue`，但这些字符串不表示本地有src目录。检查品牌和代码可确认这是“广西公安党建”另一套前端资源，不是当前“环食药数据生态”主平台。它能提供部分代码线索，不能用来编译当前数据治理门户。

## 启动、编译和HAR生成的区别

- npm start：启动本地服务器，服务已有原页面资源、工作台和后端，没有编译原Vue页面。
- build:har：从浏览器录制的HAR重新抽取HTTP响应，生成mock清单和资源；它不是前端源码编译，也不会生成Vue组件。
- 正常前端build：应从src组件、路由、样式和依赖生成dist资源；当前原平台没有这样的源码链路。

原HAR在当前目录和原压缩包中均不存在，所以现有build:har不能直接重新生成；该脚本有重建mock目录的行为，不应当作常规前端开发构建使用。

## 后续改造路径

1. 如果能够取得完整原工程，应同时取得门户和各子应用源码、package/lock文件、构建配置及原厂组件依赖，再恢复构建和对接本地后端。单独一个dist包仍然不够。
2. 如果只有当前抓取资源，长期开发宜建立新的可编译前端工程，以原平台的页面和交互作为参考，沿用现有后端能力。优先重建首页及菜单，将数据库接入、流程、质量规则和报告接入原有导航，再逐页替换旧页面。
3. 临时小改动可以使用CSS、配置和HTML注入，但应保存为明确的覆盖文件或脚本，避免分散修改多个压缩包。

第二条路线是重建可维护的前端源码，不是把原编译包自动转换成源码。可保留现有业务配置及后端接口；旧编译页面可在迁移期间继续提供。新增工作台也可作为已有功能和接口的参考实现。

当前权限、数据库、流程引擎、结果和审计后端无需因前端重建而全部重写。现有后端未实现的原厂业务仍需单独补齐，重建页面本身不能补出这些业务能力。
